# Particle-Based Material Deformation Model

## Overview

This project aims to adapt an existing particle-based dynamics model to predict material deformation. The baseline model was designed to learn collision dynamics from real-world videos by predicting the future positions and rotations of a dense set of particles. Our capstone project will investigate whether that approach can be adapted to graphite deformation observed in scanning electron microscopy (SEM) data and generated by simulation.

This document records the team's current understanding of the baseline and identifies the decisions required for the adaptation. It intentionally distinguishes reported baseline behavior from proposed work and unresolved questions. The repository does not yet contain an implementation or experimental results that validate this design.

## Expected Data Format

### Gaussian Representation

The baseline represents a scene as a set of 3D Gaussians. Each Gaussian may contain the following attributes:

| Attribute | Symbolic shape per frame | Role |
| --- | --- | --- | 
| Center or position | `[N, D]` | Used and predicted by the dynamics model | 
| Rotation | `[N, R]` | Used and predicted by the dynamics model 
| Scale | `[N, D]` or upstream-specific | Used by Gaussian reconstruction or rendering | 
| Color | `[N, C]` or upstream-specific | Used by Gaussian reconstruction or rendering |
| Opacity | `[N, 1]` or upstream-specific | Used by Gaussian reconstruction or rendering |

Here, `N` is the number of particles in a frame, `D` is the spatial dimension, `R` depends on the selected rotation representation, and `C` depends on the color representation.

A separate Gaussian Splatting algorithm can be used to produce these Gaussians. However, because the dynamics model only uses and predicts the center and rotation of each Gaussian, a 3D point cloud containing those attributes is sufficient for our purposes.

Object IDs assigning each Gaussian to separate objects are decided during preprocessing (not exactly, but its sufficient to think of it this way). Again, this in unnecessary for our purposes, as we want to predict deformation over a single material.

### Directory Layout

The Gaussian parameters for each frame should be stored in a file named `params_coarse.npz` at the following path:

```text
<scenario>/<split>/scene_XXXXX/gs/<frame>/params_coarse.npz
```

The exact arrays stored in `params_coarse.npz` still need to be documented.

## Training Flow

Three input frames are processed at a time: `t-2`, `t-1`, and `t`. For each particle it derives two motion states: 

```text
delta_x_previous = x[t-1] - x[t-2]
delta_x_current  = x[t]   - x[t-1]
```

If each frame corresponds to a time step, these can be considered the velocities per frame. The current model also uses the two most recent heights alongside the velocities, but those values are unnecessary for our purposes and are planned for removal.

Interleaved Object PointConv and Relational PointConv layers is used to model interactions among the Gaussians. Object PointConv models interactions over points belonging to the same object, while Relational PointConv models interactions between a point from one object and nearby points from other objects. At the final layer, the Gaussians' next displacement (or velocity) is predicted.

A diagram summarizing the training flow is given below:

```text
Processed videos and Gaussian particles
        |
        v
Sample a scene and starting frame
        |
        v
Construct two velocity states from three physical frames
        |
        v
Build a multiresolution KNN point-cloud hierarchy
        |
        v
Interaction PointConv backbone
        |
        v
Per-point MLP predicts proposed motion
        |
        v
Fit one rigid transform per object
        |
        v
Roll forward for three predicted frames
        |
        v
Position loss and differentiable rendering loss
        |
        v
Backpropagation with AdamW
```

## Open Questions

- How should load conditioning be implemented in the model?
- The model currently expects 3D point clouds. How should it be adapted to train on 2D point clouds?
- What should the model output: a particle's position or its velocity relative to the previous position?
- How should the model be changed so that each frame is based on changes in force rather than elapsed time?
- In the simulated data, damage is represented by a value from `0` to `1`. How should the model represent this damage?
